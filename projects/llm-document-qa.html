Enterprise RAG Assistant

A retrieval-augmented generation system for answering questions over enterprise documents, covering the parts of RAG that are usually skipped in tutorials: hybrid retrieval, cross-encoder reranking, citation validation, refusal behavior, and a systematic evaluation harness for comparing retrieval strategies.

Overview

This system enables users to query a set of enterprise policy and handbook documents using natural language and receive grounded, cited answers instead of raw search results. It's a personal/portfolio project built against a synthetic enterprise document set (ten policy and handbook documents for a fictional company) in a single-user local setup, designed to demonstrate a production-shaped RAG pipeline rather than a minimal retrieval demo: hybrid search, reranking, hard citation gating, refusal handling, query logging, and a repeatable experiment framework for comparing retrieval configurations.

Problem

Most RAG tutorials stop at "embed, retrieve, generate" and gloss over the failure modes that matter in practice: retrieval methods disagree on what's relevant, models cite sources they weren't actually given, and there's rarely a way to tell whether a change to chunking or retrieval strategy actually helped. The goal here was to build and evaluate those missing pieces directly, with measurable evidence of what worked and what didn't.

Solution

The system combines dense vector search (ChromaDB) with sparse keyword search (BM25), fuses the two into a hybrid score, and optionally reranks the merged results with a cross-encoder before generation. Answers are produced via structured output from the OpenAI API, and every claim in the response must carry a [Source N] citation. Citations aren't trusted at face value — the pipeline independently parses them out of the model's own answer and cross-checks each one against the chunks that were actually retrieved, refusing to answer rather than passing through an uncited or mis-cited claim. A separate sufficiency check refuses low-confidence queries before generation ever runs. Every retrieval configuration is swappable via YAML, which made it possible to benchmark vector-only, keyword-only, hybrid, and hybrid+reranker setups against the same labeled question set.

Architecture / Workflow

Ingestion → Section-Aware Chunking → Embeddings → Vector + BM25 Index → Hybrid Retrieval → Cross-Encoder Rerank → Grounding Check → Generation + Citation Validation → FastAPI / Streamlit

Documents are loaded from Markdown/text (with a PyMuPDF-first, pypdf-fallback path built in for PDFs) and cleaned to normalize unicode, rejoin hyphenated line-wraps, and strip control characters. Chunking is section-aware: documents are split on Markdown headings first, then any oversized section is broken into overlapping fixed-size windows (800 characters, 100-character overlap). Chunks are embedded with OpenAI's text-embedding-3-small and stored in ChromaDB, alongside a parallel BM25 keyword index. At query time, vector and keyword results are fused with weighted score combination (0.6 vector / 0.4 keyword by default), optionally reranked with a ms-marco-MiniLM-L-6-v2 cross-encoder, and checked for sufficient relevance before being handed to the LLM. The model generates a structured, cited answer through FastAPI (/chat, /documents/ingest, /evaluation/run), and a Streamlit frontend provides chat, evaluation-comparison, and live monitoring dashboards on top of the same API. The whole stack runs via Docker Compose (API + Streamlit + a Qdrant container reserved for a future vector-store swap).

Results / Impact

4 Retrieval configurations benchmarked head-to-head
71 Hand-labeled evaluation questions across 4 categories
63.4% Best Recall@5, achieved by vector-only and hybrid+reranker

Rather than assuming hybrid retrieval or reranking would automatically win, all four configurations were run against the same labeled question set and compared on recall, reciprocal rank, citation accuracy, refusal accuracy, and answer correctness. The results were informative precisely because they weren't what a tutorial would predict: naive hybrid fusion actually underperformed vector-only retrieval on Recall@5 (54.9% vs. 63.4%), while adding the cross-encoder reranker on top of hybrid retrieval recovered recall to parity with vector-only and produced the best reciprocal rank (0.60) and refusal accuracy (91.5%) — at roughly double the latency (16.9s vs. 8.3s). That kind of measured tradeoff, not a single "best" pipeline, is the actual output of the evaluation harness.

What I Built

  • Document ingestion and cleaning pipeline with section-aware Markdown chunking and a PDF extraction fallback path (PyMuPDF → pypdf)
  • Hybrid retrieval combining ChromaDB vector search and BM25 keyword search, with normalized, weighted score fusion
  • Cross-encoder reranking stage and a grounding/refusal gate based on retrieval confidence
  • Citation validation that regex-parses the model's own cited sources and cross-checks them against retrieved chunk IDs before returning an answer
  • FastAPI REST endpoints for chat, document ingestion, and evaluation, backed by structured (schema-validated) LLM output
  • A YAML-driven experiment runner that sweeps retrieval configurations and produces recall/precision/citation/refusal/correctness metrics per config
  • SQLite-backed query logging and a monitoring layer (latency, cost, refusal rate, confidence distribution)
  • Three Streamlit dashboards: chat interface, experiment comparison with a failure-case viewer, and live query monitoring
  • Docker Compose deployment (API + frontend, with a Qdrant container scaffolded for a future vector-store swap)
  • 53 pytest tests across 19 files covering chunking, retrieval, reranking, grounding, generation, evaluation metrics, and the API layer

Challenges

  • Normalizing heterogeneous relevance scores (Chroma's L2/cosine/inner-product distances and BM25's raw scores) onto a common 0–1 scale so vector and keyword results could be fused meaningfully
  • Discovering that naive hybrid fusion underperformed vector-only retrieval on Recall@5, and having to trust the evaluation numbers over the intuitive assumption that combining methods should help
  • Tracking down and fixing a bug where the experiment runner was reading from a single global settings object instead of each YAML config, which silently made all four benchmarked configurations produce identical results until the config was threaded explicitly through the retrieval and generation calls
  • Treating citation grounding as a hard, independently verified gate rather than a prompt instruction the model might not reliably follow
  • Balancing reranking's accuracy gains against its roughly 2x latency cost, and making that tradeoff visible in the evaluation results instead of hiding it

What I Learned

The most useful part of this project was building the evaluation harness before trusting any intuition about what "should" work. Hybrid retrieval and reranking are common defaults in RAG writeups, but measuring them against a labeled question set surfaced a real, counterintuitive result: hybrid fusion alone was worse than vector search alone, and only reranking on top of hybrid closed the gap — at a real latency cost. That reinforced that retrieval quality has to be measured stage by stage, not assumed from architecture diagrams, and that grounding mechanisms like citation validation are worth enforcing in code rather than leaving to prompt instructions alone. It also left me with a clear list of deliberately unfinished edges (no token-budget management in the prompt builder, stubbed Ollama/Qdrant/local-embedding providers) that mark where the system was built for extensibility rather than completeness.
