엔터프라이즈 RAG 어시스턴트

기업 문서에 대한 질문에 답하는 검색 증강 생성 시스템으로, 튜토리얼에서 흔히 생략되는 RAG의 영역들 — 하이브리드 검색, 크로스 인코더 재순위화, 인용 검증, 거부(refusal) 동작, 그리고 검색 전략을 비교하기 위한 체계적인 평가 하네스 — 를 다룹니다.

개요

이 시스템은 사용자가 자연어로 기업 정책 및 핸드북 문서 세트를 질의하고, 단순 검색 결과 대신 근거가 뒷받침된 인용 답변을 받을 수 있게 합니다. 가상의 회사를 위한 정책 및 핸드북 문서 10건으로 구성된 합성 기업 문서 세트를 대상으로 한 단일 사용자 로컬 환경의 개인/포트폴리오 프로젝트로, 최소한의 검색 데모가 아니라 프로덕션 수준의 RAG 파이프라인을 보여주도록 설계되었습니다: 하이브리드 검색, 재순위화, 엄격한 인용 게이팅, 거부 처리, 쿼리 로깅, 그리고 검색 구성을 비교하기 위한 반복 가능한 실험 프레임워크가 여기에 포함됩니다.

문제

대부분의 RAG 튜토리얼은 "임베딩, 검색, 생성"에서 멈추고, 실무에서 중요한 실패 양상들은 얼버무리고 넘어갑니다: 검색 방식마다 무엇이 관련 있는지에 대한 판단이 엇갈리고, 모델은 실제로 주어지지 않은 출처를 인용하며, 청킹이나 검색 전략을 바꾼 것이 실제로 도움이 되었는지 알 방법이 거의 없습니다. 이 프로젝트의 목표는 이러한 빠진 부분들을 직접 구축하고 평가하여, 무엇이 효과가 있었고 무엇이 없었는지에 대한 측정 가능한 근거를 확보하는 것이었습니다.

솔루션

이 시스템은 밀집 벡터 검색(ChromaDB)과 희소 키워드 검색(BM25)을 결합하고, 두 결과를 하이브리드 점수로 융합한 뒤, 생성 이전에 선택적으로 크로스 인코더로 병합된 결과를 재순위화합니다. 답변은 OpenAI API의 구조화된 출력을 통해 생성되며, 응답의 모든 주장에는 [Source N] 인용이 포함되어야 합니다. 인용은 그대로 신뢰되지 않습니다 — 파이프라인은 모델 자신의 답변에서 인용을 독립적으로 파싱한 뒤, 실제로 검색된 청크와 각각을 교차 검증하며, 인용이 없거나 잘못 인용된 주장을 그대로 통과시키는 대신 답변을 거부합니다. 별도의 충분성 검사는 생성이 실행되기 전에 신뢰도가 낮은 쿼리를 거부합니다. 모든 검색 구성은 YAML로 교체 가능하며, 이 덕분에 동일한 라벨링된 질문 세트를 대상으로 벡터 전용, 키워드 전용, 하이브리드, 하이브리드+재순위화 구성을 벤치마킹할 수 있었습니다.

아키텍처 / 워크플로우

수집 → 섹션 인식 청킹 → 임베딩 → 벡터 + BM25 인덱스 → 하이브리드 검색 → 크로스 인코더 재순위화 → 그라운딩 검사 → 생성 + 인용 검증 → FastAPI / Streamlit

문서는 Markdown/텍스트에서 로드되며(PDF의 경우 PyMuPDF를 우선 시도하고 pypdf로 폴백하는 경로가 내장되어 있습니다), 유니코드를 정규화하고 하이픈으로 줄바꿈된 단어를 다시 이어붙이며 제어 문자를 제거하는 방식으로 정제됩니다. 청킹은 섹션을 인식하는 방식으로 이루어집니다: 문서는 먼저 Markdown 헤딩 기준으로 분할되고, 그 후 크기가 큰 섹션은 겹치는 고정 크기 윈도우(800자, 100자 오버랩)로 다시 나뉩니다. 청크는 OpenAI의 text-embedding-3-small로 임베딩되어 ChromaDB에 저장되며, 병렬로 BM25 키워드 인덱스도 함께 저장됩니다. 쿼리 시점에는 벡터 결과와 키워드 결과가 가중치 기반 점수 조합(기본값 벡터 0.6 / 키워드 0.4)으로 융합되고, 선택적으로 ms-marco-MiniLM-L-6-v2 크로스 인코더로 재순위화된 뒤, LLM에 전달되기 전에 충분한 관련성이 있는지 검사됩니다. 모델은 FastAPI(/chat, /documents/ingest, /evaluation/run)를 통해 구조화된 인용 답변을 생성하며, Streamlit 프론트엔드는 동일한 API 위에서 채팅, 평가 비교, 실시간 모니터링 대시보드를 제공합니다. 전체 스택은 Docker Compose(API + Streamlit + 향후 벡터 스토어 교체를 위해 예약된 Qdrant 컨테이너)로 실행됩니다.

결과 / 영향

4 서로 정면으로 벤치마킹한 검색 구성 수
71 4개 카테고리에 걸친 수작업 라벨링 평가 질문 수
63.4% 벡터 전용 및 하이브리드+재순위화가 달성한 최고 Recall@5

하이브리드 검색이나 재순위화가 자동으로 더 나은 결과를 낼 것이라고 가정하는 대신, 네 가지 구성 모두를 동일한 라벨링된 질문 세트로 실행하여 재현율, 역순위(reciprocal rank), 인용 정확도, 거부 정확도, 답변 정확성을 비교했습니다. 그 결과는 튜토리얼이 예측할 법한 내용과 달랐기 때문에 유의미했습니다: 단순한 하이브리드 융합은 Recall@5에서 오히려 벡터 전용 검색보다 낮은 성능(54.9% 대 63.4%)을 보였고, 하이브리드 검색에 크로스 인코더 재순위화를 추가하자 재현율이 벡터 전용 수준으로 회복되었을 뿐 아니라 최고의 역순위(0.60)와 거부 정확도(91.5%)를 기록했습니다 — 다만 지연 시간은 약 두 배(16.9초 대 8.3초)였습니다. 단 하나의 "최고" 파이프라인이 아니라 이러한 정량적인 트레이드오프를 보여주는 것이 이 평가 하네스가 실제로 만들어내는 결과물입니다.

구현 내용

  • 섹션 인식 Markdown 청킹과 PDF 추출 폴백 경로(PyMuPDF → pypdf)를 갖춘 문서 수집 및 정제 파이프라인
  • ChromaDB 벡터 검색과 BM25 키워드 검색을 결합하고, 정규화된 가중치 점수 융합을 적용한 하이브리드 검색
  • 크로스 인코더 재순위화 단계와 검색 신뢰도 기반의 그라운딩/거부 게이트
  • 모델 자신이 인용한 출처를 정규식으로 파싱하여 답변 반환 전에 검색된 청크 ID와 교차 검증하는 인용 검증 로직
  • 구조화(스키마 검증)된 LLM 출력을 기반으로 하는, 채팅·문서 수집·평가용 FastAPI REST 엔드포인트
  • 검색 구성을 순회하며 구성별로 재현율/정밀도/인용/거부/정확성 지표를 산출하는 YAML 기반 실험 러너
  • SQLite 기반 쿼리 로깅과 모니터링 계층(지연 시간, 비용, 거부율, 신뢰도 분포)
  • 세 가지 Streamlit 대시보드: 채팅 인터페이스, 실패 사례 뷰어를 갖춘 실험 비교, 실시간 쿼리 모니터링
  • Docker Compose 배포(API + 프론트엔드, 향후 벡터 스토어 교체를 위해 미리 구성된 Qdrant 컨테이너 포함)
  • 청킹, 검색, 재순위화, 그라운딩, 생성, 평가 지표, API 계층을 아우르는 19개 파일에 걸친 53개의 pytest 테스트

어려웠던 점

  • 이질적인 관련성 점수(Chroma의 L2/코사인/내적 거리와 BM25의 원시 점수)를 공통된 0–1 스케일로 정규화하여 벡터와 키워드 결과를 의미 있게 융합할 수 있도록 만드는 작업
  • 단순한 하이브리드 융합이 Recall@5에서 벡터 전용 검색보다 낮은 성능을 보인다는 사실을 발견하고, "방법을 결합하면 도움이 될 것"이라는 직관보다 평가 수치를 신뢰해야 했던 경험
  • 실험 러너가 각 YAML 구성이 아니라 하나의 전역 설정 객체를 읽고 있던 버그를 추적하여 수정한 일 — 이 버그로 인해 벤치마킹된 네 가지 구성 모두가 동일한 결과를 냈지만, 설정 값을 검색 및 생성 호출 전체에 명시적으로 전달하기 전까지는 이를 알아차리지 못했음
  • 인용 그라운딩을 모델이 안정적으로 따르지 않을 수도 있는 프롬프트 지시가 아니라, 독립적으로 검증되는 엄격한 게이트로 다루기
  • 재순위화가 가져오는 정확도 향상과 약 2배의 지연 시간 비용 사이의 균형을 맞추고, 이 트레이드오프를 감추지 않고 평가 결과에 드러나도록 만들기

배운 점

이 프로젝트에서 가장 유익했던 부분은 무엇이 "효과가 있어야 하는지"에 대한 직관을 신뢰하기 전에 평가 하네스를 먼저 구축한 것이었습니다. 하이브리드 검색과 재순위화는 RAG 관련 글에서 흔히 기본값으로 등장하지만, 라벨링된 질문 세트로 실제 측정해 보니 직관에 반하는 결과가 드러났습니다: 하이브리드 융합만으로는 벡터 검색 단독보다 성능이 낮았고, 하이브리드 위에 재순위화를 추가했을 때만 그 격차가 좁혀졌으며 이는 실제 지연 시간 비용을 수반했습니다. 이는 검색 품질을 아키텍처 다이어그램만으로 가정하는 것이 아니라 단계별로 측정해야 한다는 점, 그리고 인용 검증과 같은 그라운딩 메커니즘은 프롬프트 지시에만 맡기지 않고 코드로 강제할 가치가 있다는 점을 다시 확인시켜 주었습니다. 또한 이 과정에서 프롬프트 빌더의 토큰 예산 관리 부재, 스텁으로만 구현된 Ollama/Qdrant/로컬 임베딩 프로바이더 등 의도적으로 마무리하지 않은 부분들의 명확한 목록도 남았는데, 이는 이 시스템이 완결성보다는 확장성을 염두에 두고 만들어졌음을 보여줍니다.
